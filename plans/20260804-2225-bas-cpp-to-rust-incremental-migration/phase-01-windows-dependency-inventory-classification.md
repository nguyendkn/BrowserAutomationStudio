**Correction found during this plan's drafting (verify again at execution time, don't assume stale):** the coordinator's grep for "COM usage" used the pattern `CoCreateInstance|IUnknown|__declspec|CComPtr` and reported Modules 9 files / Engine 3 / Studio 1 / ChromeWorker 1, framing this as "the single highest-value architectural target" needing a COM-based plugin-loading redesign. A grep for the REAL COM APIs alone (`CoCreateInstance|QueryInterface|__uuidof|IID_|CComPtr|CoInitialize`, excluding `__declspec`), **scoped to C/C++ source (`*.cpp`/`*.h`/`*.hpp`/`*.cc`)**, returns **zero matches in any BAS-authored or vendored C/C++ file**. (An UNSCOPED repo-wide grep also hits 2 non-C++ assets that are not load-bearing for this classification: `ChromeWorker/html/toolbox/vs/basic-languages/src/cpp.js`, a bundled Monaco editor language file whose keyword list contains the string `__uuidof`, and `Modules/SQL/js/manifest.json`, a bundled Sequelize JS dependency whose code contains the string `QueryInterface` — both are third-party JS/JSON assets, not BAS C++ source, and don't affect any compile/link decision.) Every one of the flagged C/C++ files uses `__declspec(dllexport)`/`__declspec(dllimport)`/`__declspec(thread)` — plain MSVC export/import/TLS keywords, not COM. Evidence: `Solution/Modules/DateTime/dll/moduledll.h` (and 8 sibling `moduledll.h` files) export `extern "C"` functions via `__declspec(dllexport)` only; `Solution/Engine/oauth/o0export.h:7,9` and `Solution/Engine/snappy/snappy-c.h:38,40` are dllexport/dllimport macros; `Solution/Engine/debug_memory/c++11.h:300` is `__declspec(thread)` (TLS). **Reclassify Modules' export mechanism from category (d) to category (b)** — `__declspec(dllexport)` has a one-line portable equivalent (`#if defined(_WIN32) ... #else __attribute__((visibility("default"))) ... #endif`, or nothing at all — POSIX shared libraries export `extern "C"` symbols by default).
- **The actual plugin-LOADING mechanism (the other half of the "is this COM?" question) is already cross-platform.** `Solution/Engine/modulemanager.cpp` loads each Module DLL via Qt's `QLibrary` (`#include <QLibrary>` at line 9; `new QLibrary(...)`, `->load()`, `->resolve(...)` at lines 697-767) — `QLibrary` is Qt's own cross-platform dynamic-library abstraction (`.dll`/`.dylib`/`.so` transparently, backed by `LoadLibrary`/`dlopen` internally). There is no COM registration, no `LoadLibrary`/`GetProcAddress` call in `modulemanager.cpp` at all. The Modules plugin system does NOT need a `libloading`+`cxx` redesign — it already works cross-platform at the loader level; only the DLL-side export macro (category b, trivial) is Windows-specific.
- **Genuine Windows-only `LoadLibrary`/`GetProcAddress` calls DO exist in Engine, but unrelated to Modules**: `Solution/Engine/CrashHandler.cpp:166,206` loads `dbghelp.dll` for crash-dump generation (Windows-specific crash API — category c, no cross-platform equivalent, needs a `#[cfg(target_os = "windows")]` no-op/alternative on other OSes); `Solution/Engine/devicescalemanager.cpp:29,32` loads `Shcore.dll` for DPI-scaling (Windows-specific — category c). Both are small, isolated, 1 file each.
- **A separate genuine `OpenProcess`/`HANDLE` call site**, distinct from the `LoadLibrary` sites above: `Solution/Engine/webdriverprocesscomunicatorfactory.cpp:15,55` (`#include <Windows.h>`; `HANDLE process = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid);`) — process-existence/query check, category (b), maps directly to the `sysinfo` crate's process-lookup API. Verified by reading the file directly; not to be confused with `processdeleter.cpp` (windows.h include is dead — body only calls portable `QProcess::kill()`/`deleteLater()`, category a) or `memoryinfo.cpp` (calls `GlobalMemoryStatusEx`, already `Q_OS_WIN`-guarded with a placeholder fallback, category b) — three different files, three different WinAPI stories, easy to conflate if classifying by filename-list alone instead of reading each file.
- **CEF has zero macOS build-config today**: grep across every `.pro` file in the repo for `macx`/`Q_OS_MAC`/`__APPLE__` returns nothing — no `.pro` file has ever had a mac branch. `ChromeWorker.pro:168`'s `LIBS +=` line unconditionally links `-lAdvapi32 -luser32 -lPsapi -lshell32 -lDbgHelp -lComdlg32 -lgdi32` (Windows system libs) alongside CEF in one unconditional line — CEF itself ships macOS binaries/frameworks, but BAS's qmake config has never been taught how to link against them. This is real work (a `macx { ... }` qmake block with mac-appropriate CEF framework paths + mac system libs), not a toggle — but it is qmake/build-config work, not a Rust-migration task.

## Requirements
- Functional: produce `docs/macos-blocker-classification.md` — a per-file (ideally per-call-site) table covering every `windows.h`/`_WIN32`/WinAPI-symbol hit across ALL modules (not just Engine/ChromeWorker), each row tagged with exactly one category: **(a) incidental/removable** (include with no real platform dependency — can just delete or leave unguarded since it's unused), **(b) trivially portable** (has a direct cross-platform crate/macro equivalent — `sysinfo` for process info, `std::net`/`tokio` for WinSock networking, a portable export macro for `__declspec(dllexport)`), **(c) genuinely OS-specific** (wrap behind a `#[cfg(target_os = "windows")]`-gated trait in the new `bas-platform` crate, with a real or no-op alternative for macOS/Linux), **(d) architecturally significant redesign needed** (reserved for a case actually proven to need one — Modules' export mechanism no longer qualifies per this phase's own correction above; re-verify no other (d) candidate exists before closing this phase).

## ADR Rationale
**Decision:** Run a fresh, cited, per-file classification pass in this phase rather than taking the coordinator's module-level grep counts (including the "COM usage" framing) at face value into Phase 2's implementation order.
**Why:** the "COM usage: 9 Modules files, architecturally serious" claim was falsified with concrete evidence during this plan's own drafting (zero real COM APIs in any BAS C/C++ source, confirmed by a grep for `CoCreateInstance|QueryInterface|__uuidof|IID_|CComPtr|CoInitialize` scoped to `*.cpp`/`*.h`/`*.hpp`/`*.cc`) — building Phase 2 around a redesign that isn't needed would waste the plan's first and most schedule-sensitive milestone on a non-problem, and worse, would risk under-scoping the REAL Tier-1 item (ChromeWorker's 36 files). Per this plan's own Role Core discipline ("when the user heads the wrong way, say so directly with evidence"), the correction is made here, cited, and carried forward into Phase 2's re-ranked priority order.
**Alternatives rejected:** accept the coordinator's "Modules COM redesign, top priority" framing unverified (would misallocate Phase 2's effort and mischaracterize the plan's actual risk profile); silently reorder Phase 2 without documenting why (would look like an unexplained deviation from an explicit instruction, and would lose the evidence trail if the correction itself is later questioned).
