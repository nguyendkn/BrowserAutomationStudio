## Overview
- **Priority:** P3 — **deferred cross-platform hardening track. This phase is NOT a gate and NOT a precondition for any other phase.** Per the user's 2026-09-18 reprioritization, Windows is BAS's real production platform (v25.8.0 ships there today) and the plan's first milestone is the Windows-validated incremental migration (Phase 3 onward). The macOS build+launch work below is still real, still planned, and still wanted — it is simply **scheduled after or alongside the Phase 3-12 module migrations**, not in front of them. Nothing in Phase 3 onward waits on this phase's completion.
- **Status:** pending, unscheduled. Depends on Phase 1's classification table; may run at any point once Phase 1's classification exists.
- **Scheduling / file-ownership rule (important):** this phase edits WinAPI-touching C++ call sites inside ChromeWorker, Engine, and Modules — the same files Phase 6, 8, and 11 fully port to Rust. Do NOT run this phase concurrently with those phases on the same module. Whichever track reaches a module first owns it: if this phase fixes ChromeWorker's call sites first, Phase 6 integrates the existing `bas-platform` calls into its crate structure; if Phase 6 ports ChromeWorker first, its Rust code handles cross-platform primitives natively and this phase's ChromeWorker tier is dropped as already-done. Either order is valid — record which happened, don't do both.
- Scope: **narrow, surgical fixes only** — replace or platform-abstract the SPECIFIC blocking call sites Phase 1 identified, via a small new Rust crate (`bas-platform` for portable primitives) called from the STILL-UNPORTED C++ via `cbindgen`. This is explicitly NOT a full rewrite of Engine/ChromeWorker/Modules — that's the Phase 3-12 critical path. Also covers the CEF-macOS qmake build-config work (not Rust) needed for the same launch goal.

## Key Insights
- Phase 1's corrected classification changes this phase's priority order from the original "Modules first" framing: **Tier 1 is ChromeWorker's 36 `windows.h` files** (the largest real blocker), **Tier 2 is Engine's 13 `windows.h` files + 2 genuine `LoadLibrary` sites** (`CrashHandler.cpp` dbghelp.dll, `devicescalemanager.cpp` Shcore.dll) **+ the `OpenProcess`/`HANDLE` site** (`webdriverprocesscomunicatorfactory.cpp`) **+ `memoryinfo.cpp`'s `GlobalMemoryStatusEx` fallback upgrade**, **Tier 3 is Modules' TWO real `windows.h` files** (`Modules/UserNotification/dll/moduledll.cpp`, `Modules/Timezones/dll/maxminddb.c`) **+ the 9 trivial `__declspec`-only export headers** (cheap, batch together — no plugin-loader redesign needed, since `modulemanager.cpp`'s `QLibrary`-based loading is already cross-platform), **Tier 4 is the remaining smaller modules** (WebInterfaceBrowser 5, Studio 3, SchedulerBrowser 2, Scheduler 2, ShopViewer 1, RemoteExecuteScript 1). Note: `processdeleter.cpp`'s `windows.h` include is dead (category a) — removed alongside Tier 2, not a real fix.
- Because this phase touches call sites inside modules that are NOT yet fully ported to Rust (ChromeWorker/Engine/Modules full migration is Phase 6/8/11), the fix pattern here is deliberately small: a new `bas-platform` crate exposing cross-platform primitives (process info via `sysinfo`, portable export-macro equivalents, a `#[cfg(target_os)]`-gated trait for the genuinely OS-specific cases) via a `cbindgen`-generated C header, called from the UNCHANGED surrounding C++ at just the blocking line. This is narrower than a `cxx` bidirectional bridge because these call sites don't need C++ to call back into Rust — they just need a portable C function to call instead of a WinAPI one.
- CEF-on-macOS is a parallel, non-Rust track: Phase 1 found zero `macx {}` qmake blocks anywhere in the repo and `ChromeWorker.pro`'s `LIBS +=` line unconditionally links Windows system libs alongside CEF. This phase must add real `macx { }` blocks to `ChromeWorker.pro`, `WebInterfaceBrowser.pro`, `SchedulerBrowser.pro`, and `Engine.pro` with mac-appropriate CEF framework paths and mac system libs (dropping the Windows-only `-lAdvapi32 -luser32 -lPsapi -lshell32 -lDbgHelp -lComdlg32 -lgdi32` on that platform) — this is qmake/build-config work, verified against Phase 1's CEF-SDK-availability finding, not a code port.
- Golden-file characterization tests (per this plan's own hard constraint) must exist for each call site BEFORE it's touched — using Phase 1’s Windows reference build (the plan’s PRIMARY validation target) as the pre-change behavior snapshot.

## Requirements
- Functional: every category-(b) call site (Phase 1) is replaced with a cross-platform crate/macro; every category-(c) call site is wrapped behind a `#[cfg(target_os)]`-gated trait in `bas-platform` with a real or explicitly-no-op alternative on macOS/Linux; category-(a) sites are removed or left unguarded (no behavior to preserve).
- Non-functional: for every call site touched, a before/after characterization test exists (behavior on Windows, via Phase 1’s Windows reference build, unchanged) before AND after the change — no call site is "fixed" without a regression check.
- CEF's macOS build-config work is verified against real CEF mac binaries (Phase 1's availability finding), not assumed to compile blind.
- **This phase’s own (non-gating) completion criterion:** `BrowserAutomationStudio.exe`'s macOS equivalent (whatever the qmake target produces on `macx`) builds from a clean checkout on a macOS CI runner (GitHub Actions `macos-latest`) or local macOS dev machine, and launches — even though the vast majority of Engine/ChromeWorker/Modules business logic is still unported C++. Only the specific blocking call sites need to be resolved for this criterion; full-logic correctness on macOS (e.g. does every script function actually WORK on macOS) is explicitly out of scope until the Phase 4–12 critical path ports the real logic. **This criterion gates nothing outside this phase** — Phase 3 onward is gated on Windows builds only (plan.md, “Per-phase checkpoint”).
- **No Windows regression:** because this phase edits C++ that ships on Windows today, every fix must keep the Windows build green. That is the binding constraint here, above the macOS outcome.

## Architecture
- **New crate `bas-platform`** (`rust/bas-platform/`): cross-platform OS primitives used by call sites across MULTIPLE still-C++ modules (justifies its own crate — a genuinely cross-cutting concern per the corrected repo-wide scan, not a fragment of any one module). Internal modules: `process` (via `sysinfo`, replacing any raw process-handle WinAPI), `export_macro` (a `cbindgen`-friendly portable dllexport equivalent, mostly a documentation/build-config change on the C++ side rather than Rust logic), `platform_trait` (the `#[cfg(target_os)]`-gated trait for genuinely OS-specific cases like `CrashHandler.cpp`'s crash-dump API and `devicescalemanager.cpp`'s DPI-scaling API — Windows arm uses the existing WinAPI logic ported as-is, macOS/Linux arm is a real equivalent where one exists or a documented no-op where none does).
- Exposed to still-C++ callers via `cbindgen`-generated C header (researcher-02's recommended direction for "self-contained Rust module → C++ caller") — no `cxx` bidirectional bridge needed here since C++ doesn't need to call back into anything stateful.
- `bas-platform` is reused (not reimplemented) by Phase 6’s `bas-chromeworker` and Phase 8’s `bas-engine-core` `platform` submodules **if this phase has run by then**. Because this phase is no longer scheduled first, that dependency is conditional: Phase 6/8 depend on `bas-platform` if it exists, otherwise they implement their own `platform` submodule and this phase consolidates the duplication when it runs (recorded in plan.md’s crate table and in phase-06/phase-08).
- **Workspace root is NOT created here.** `rust/Cargo.toml` is owned by Phase 4 (the critical path’s first crate-producing phase). If this phase somehow runs before Phase 4, it creates the workspace root and Phase 4 adopts it; the default assumption is that Phase 4 already created it and this phase only adds `bas-platform` as a member.
- CEF-macOS build-config: `macx { LIBS += -F<cef-framework-path> -framework "Chromium Embedded Framework" ... INCLUDEPATH += <cef-mac-sdk-include> }` blocks added per Phase 1's SDK-availability finding, alongside (not replacing) the existing Windows `LIBS +=` line.

## Implementation Steps

For each Tier-1 (ChromeWorker) call site: write a golden characterization test against the Windows reference build (Phase 1) capturing current behavior, then replace the call site with `bas-platform` or a portable equivalent, then re-run the golden test against the (still Windows-built) result to confirm no behavior change, THEN attempt the macOS build again — expect the macOS build to progress further each time a blocking site is removed.

8. Re-run the Phase 1 Windows reference build at the end to confirm zero Windows regression from the full set of fixes.
7. Document every fix applied (call site → category → fix) in `docs/macos-blocker-classification.md`, updating each row's status from "classified" to "fixed, verified."

## Success Criteria
- **Windows stays green:** Phase 1’s Windows reference build passes after every tier’s fixes — the binding constraint, since Windows is the shipping platform.
- **A clean checkout builds and BAS (or its qmake-defined macOS launch target) launches on macOS** — evidenced by a green `macos-latest` CI run with a passing smoke-launch step. This is this phase’s completion criterion; **no other phase depends on it**.
- Every Tier 1-4 call site has a passing before/after characterization test (via Phase 1’s Windows reference build) proving the fix didn't change Windows behavior.
- CEF's macOS build-config compiles and links against real CEF mac binaries (not a stub) — evidenced by the mac build actually invoking CEF APIs, not just skipping that code path.
- `bas-platform` builds and unit-tests on macOS + Linux in CI — this crate's own cross-platform readiness checkpoint, and the foundation Phase 6/8 reuse.

## Risk Assessment
- **A category-(c) call site has no real macOS equivalent and BAS's behavior genuinely degrades there** (e.g. `CrashHandler.cpp`'s Windows crash-dump mechanism) — mitigated by an explicit, documented no-op or reduced-functionality fallback (e.g. macOS gets a basic signal-handler-based crash log instead of `dbghelp.dll`'s minidump) rather than silently pretending parity; record the gap in `docs/macos-blocker-classification.md`, don't hide it.
- **CEF mac SDK licensing/availability blocks the build-config track** — if Phase 1 found this unresolved, this phase cannot fully complete; escalate to the user rather than shipping a macOS build that compiles but can't actually launch a browser (legitimate dependency-conflict defer reason, per this plan's own escalation rules).
- **Fixing 36+ ChromeWorker call sites individually risks touching behavior beyond the blocking line** — mitigated by keeping each fix to the SMALLEST possible diff (replace exactly the WinAPI call, not surrounding logic) and the per-call-site golden test in step 2, not a batch fix-then-test-everything-at-the-end approach.
- **This phase's macOS build success doesn't mean the APP works on macOS** — only the specific blockers are resolved; Engine/ChromeWorker/Modules business logic is still unported C++ and may behave incorrectly at runtime for reasons unrelated to WinAPI (e.g. file-path assumptions, case-sensitivity). This is explicitly accepted scope (Overview) — full functional correctness on macOS follows the Phase 4–12 ports.
- **Double-editing a module with the critical path** — this phase and Phase 6/8/11 touch the same C++ files. Mitigated by the Overview’s ownership rule (first track to reach a module owns it); the concrete failure mode is merge conflict plus lost fixes, so the two tracks must never run the same module concurrently.
- **Being deferred indefinitely** — a non-gating track can be starved forever. Mitigated by scheduling it explicitly (e.g. between Phase 6 and Phase 7, or immediately after Phase 12) rather than leaving it “whenever”; record the chosen slot in plan.md when it’s picked.

## Security Considerations
- `bas-platform`'s `c_abi.rs` (the `cbindgen`-exposed surface called from unmodified C++) is a new `unsafe` concentration point — same containment discipline as every other phase's `platform`/`c_abi` module: confine `unsafe`, document ownership of every pointer crossing the boundary.
- `CrashHandler.cpp`'s fallback behavior on macOS (Risk Assessment) must not silently disable crash reporting without a recorded decision — a security-relevant regression if crash telemetry feeds into an incident-response process.
- The portable export-macro fix for Modules (`__attribute__((visibility("default")))`) changes symbol visibility semantics on POSIX — verify it doesn't inadvertently export MORE symbols than the Windows `__declspec(dllexport)` did (e.g. an explicit visibility-hidden default for the rest of the translation unit, matching current Windows behavior where only `dllexport`-marked symbols are visible).

## Test Strategy & Quality Gate
Lane `high-risk`.
- **Spec:** Goal — resolve every macOS-blocking call site with the smallest possible diff, reach a working macOS build+launch. AC: Given Phase 1's classification table, When each call site's fix is applied, Then its before/after characterization test passes (no Windows behavior change) AND the macOS build progresses past that blocker; Given all Tier 1-4 fixes + CEF mac build-config, When a clean checkout builds on `macos-latest` CI, Then the app launches and the smoke-launch step passes. I/O contract: N/A per call site (behavior-preserving point fixes); the macOS launch target's process-alive/window-creation signal is the aggregate I/O contract for the phase gate. Out-of-scope: full business-logic correctness on macOS, any category-(d) redesign (none found per Phase 1), full ChromeWorker/Engine/Modules migration (Phase 4+).
- **Pyramid:** ~60% unit (`bas-platform`'s own Rust tests), ~20% integration (per-call-site before/after characterization against the Windows reference build), ~20% e2e (the macOS build+smoke-launch gate itself).
- **E2E scenario:** "Clean checkout on macOS CI → build → launch → process-alive check" — this phase’s e2e criterion. Plus "Windows reference build after all fixes → build → launch" as the regression e2e.
- **Coverage target:** ≥90% line / ≥75% branch diff-coverage on `bas-platform`'s new Rust code, via `cargo tarpaulin`. The C++-side point fixes are covered by the before/after characterization tests, not a Rust coverage number (most of the diff is C++ call-site edits, not new Rust logic).
- **Evidence commands:** `macos-latest` CI run log (build + smoke-launch pass), each Tier's before/after characterization diff output, `cargo test -p bas-platform`, `cargo tarpaulin -p bas-platform --out Html`.

## ADR Rationale
**Decision:** Fix the macOS-blocking call sites via small, targeted new Rust crates (`bas-platform`) called from otherwise-unported C++, rather than either (a) fixing them in pure C++ with `#ifdef` guards and no Rust at all, or (b) waiting until each module's full Rust port (Phase 4+) to address them.
**Why:** macOS support is still a real, wanted goal — it is just no longer FIRST (2026-09-18 reprioritization: Windows, the shipping platform, is the plan’s first milestone). Given the work happens at all, doing it as a small `bas-platform` Rust crate rather than pure-C++ `#ifdef` guards avoids doing the same call sites twice: Phase 6/8’s ports would otherwise have to redo them in Rust anyway. Keeping the fixes surgical (rather than folding them into Phase 6/8/11’s full ports) preserves the option to run this track independently, in whatever slot it gets scheduled, without blocking the critical path. Original framing (pre-2026-09-18) had “start được project on macOS as FIRST milestone” — that ordering is superseded.
**Alternatives rejected:** pure C++ `#ifdef` fixes with no Rust (achieves the launch goal but wastes the opportunity to seed `bas-platform` early, meaning Phase 6/8 would duplicate this cross-platform-primitive work later); defer all WinAPI fixes to each module's full Rust port (rejected — misses the user's explicit "unblock macOS first" reprioritization, pushes the milestone out by months).
