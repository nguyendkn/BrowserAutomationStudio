## Findings

1. **BLOCKER** (confidence 9) — `bas-fastexecute` crate-count/definition contradiction.
   - Quote (plan.md:37-40): "`FastExecuteScript` gets no dedicated crate — scout labels it a thin in-process wrapper blocked on Engine; it becomes a minimal binary against `bas-engine-script` (Phase 10). Studio + ShopViewer are excluded from the committed 8 (scout: negligible value) — optional 9th crate or stays C++ wrapping Rust via CXX-Qt, decided at Phase 11."
   - Quote (phase-10-modules-migration.md:29): "`FastExecuteScript` becomes `rust/bas-fastexecute/` — a `[[bin]]`-only crate (no library surface), depending on `bas-engine-script` + `bas-engine-plugin` directly. This is the one exception to \"everything is a lib crate\" in the workspace..."
   - Quote (phase-10-modules-migration.md:35): "**Create:** `/Users/nguyendk/Documents/projects/me/bas/rust/bas-fastexecute/{Cargo.toml,src/main.rs}`."
   - Quote (phase-11-consolidation-cleanup.md:24): "Final workspace layout (`rust/Cargo.toml` members): `bas-contracts`, `bas-browser-shell`, `bas-scheduling`, `bas-chromeworker`, `bas-engine-core`, `bas-engine-script`, `bas-engine-plugin`, `bas-modules`, `bas-fastexecute`, and optionally `bas-studio` if Studio/ShopViewer's decision ... is to migrate."
   - Quote (phase-08-engine-script-migration.md:27): "...do not create additional top-level crates for it (respects the workspace's 8-crate ceiling)."
   - Explanation: plan.md's architecture section explicitly caps the committed crate set at 8 and states FastExecuteScript will NOT be a dedicated crate, reserving the only "optional 9th" slot for Studio. Phase 10 and Phase 11 directly contradict this: they create `bas-fastexecute` as a full Cargo workspace member (own `Cargo.toml`, own binary target, listed by name in the "Final workspace layout"), making it a de-facto 9th crate before Studio's decision even happens — and Phase 11 lists Studio as a further *10th*, optional member on top of that. Phase 08 independently reaffirms an "8-crate ceiling" that phases 10/11 already violate. This is a scope/ownership contradiction per the rubric, not mere wording drift: readers of plan.md alone would build a 9-crate workspace incorrectly (leaving out `bas-fastexecute`, or conflating it with the Studio decision slot).
   - Variant check: grepped for other "no dedicated crate" claims — none found elsewhere; this is isolated to FastExecuteScript.

2. **MINOR** (confidence 8) — Phase 11 self-contradicts its own crate count.
   - Quote (phase-11-consolidation-cleanup.md:14): "By this point, 7 of the 8 committed crates exist (`bas-contracts`, `bas-browser-shell`, `bas-scheduling`, `bas-chromeworker`, `bas-engine-core`, `bas-engine-script`, `bas-engine-plugin`, `bas-modules`) — this phase is about tidying the SEAMS between them..."
   - Explanation: the parenthetical lists exactly 8 crate names but the sentence says "7 of the 8." Since Phase 11 depends on Phase 10 (which is where `bas-modules`, the 8th, is completed — phase-10 Overview:10 "Depends on Phase 9 complete", and Phase 11 Overview:10 "Depends on Phase 10"), by the time Phase 11 starts all 8 should exist; the "7 of 8" figure is simply wrong (off-by-one), independent of Finding 1's `bas-fastexecute` issue.

3. **MINOR** (confidence 8) — Misattributed quote: "tightly coupled" credited to scout, actually researcher-04's wording.
   - Quote (plan.md:31): "`bas-chromeworker` | ChromeWorker (CDP client, fingerprinting, tab/input control) | Scout: \"self-contained... tightly coupled\" — splitting cuts a cohesive unit"
   - Quote (phase-05-chromeworker-migration.md:4): "`scout/scout-01-module-map.md` — ChromeWorker (~320 files, CEF-based, NO Qt, 43 WinAPI/COM files, \"self-contained... tightly coupled... isolated from rest of codebase\")."
   - Quote (phase-05-chromeworker-migration.md:89): "**Why:** both scout (\"self-contained... tightly coupled\") and researcher-04 (explicit recommendation) agree..."
   - Verified: scout-01-module-map.md contains "self-contained" (line 19: "self-contained (minimal Engine deps)"; line 148: "isolated from rest of codebase; protocol-heavy but self-contained") but never the phrase "tightly coupled" anywhere in the file (grep confirmed zero matches). "tightly coupled" is researcher-04's own language: research/researcher-04-crate-architecture.md:29 "ChromeWorker (224 files): Keep as one crate (fingerprinting + browser control are tightly coupled; high cohesion)."
   - Explanation: plan.md and phase-05 splice a scout phrase and a researcher-04 phrase into one string and attribute the whole thing to "Scout." The underlying single-crate decision is still supported by real content in both sources, so this doesn't invalidate the decision, but it misrepresents what scout actually found (scout never assessed ChromeWorker's *internal* cohesion, only its external isolation/no-Qt status). Bonus: researcher-04 estimates ChromeWorker at 224 files vs scout's ~320 — neither plan.md nor phase-05 reconcile this, though all phases consistently use scout's 320 figure elsewhere, so it doesn't propagate further.

4. **MINOR** (confidence 7) — Quoted scout text not found verbatim; paraphrase presented as quotation.
   - Quote (phase-06-engine-boundary-discovery.md:15): "Scout's own dependency map already implies the seam: \"40 plugin Modules ... ALL blocked on Engine's script function registry (an integration-point dependency, not a coupling problem)\"..."
   - Quote (phase-09-engine-plugin-registry-migration.md:6): "`scout/scout-01-module-map.md` — \"40 plugin Modules ... ALL blocked on Engine's script function registry ... cannot move meaningfully before Engine exposes a stable interop boundary.\""
   - Verified via grep: this exact string does not appear in scout-01-module-map.md. The closest actual scout text is line 123: "Engine is the bottleneck: Core library consumed by Studio, FastExecuteScript, RemoteExecuteScript, Updater, and all 40 Modules (via registration). Any migration must address Engine first or design robust FFI layer."
   - Explanation: substance is roughly consistent (Modules do depend on Engine per scout), but the quotation marks imply verbatim sourcing that doesn't exist — a paraphrase dressed as a citation. Doesn't change the plan's technical conclusions but is a documentation-accuracy gap the rubric's anti-hallucination framing would flag if it were load-bearing for a design choice (here it isn't — the plugin-registry-last ordering is independently justified by plan.md:44-46's own reasoning).

5. **NEEDS CONFIRMATION** (confidence 6) — Plan's crate grouping silently diverges from researcher-04's explicit recommendation for SchedulerBrowser/FastExecuteScript.
   - Quote (research/researcher-04-crate-architecture.md:33): "4. **Utilities:** Merge Scheduler, SchedulerBrowser, FastExecuteScript, RemoteExecuteScript into `bas-scheduling` (responsibility-based grouping)."
   - Quote (plan.md:29): "`bas-browser-shell` | WebInterfaceBrowser + SchedulerBrowser (CEF, no Qt) | Both ~independent, ~29 files combined — 2 crates would be over-fragmentation"
   - Quote (plan.md:30): "`bas-scheduling` | Scheduler + Updater + RemoteExecuteScript | Scout: shared HTTP/ZIP/task business logic, no Qt dep on Engine, natural cohesion"
   - Explanation: plan.md groups SchedulerBrowser with WebInterfaceBrowser (not Scheduler/Updater/RemoteExecuteScript as researcher-04 recommended) and gives FastExecuteScript no crate in `bas-scheduling` either (it later surfaces as the separate `bas-fastexecute`, Finding 1). Plan.md justifies its OWN grouping via scout's coupling facts (CEF-vs-HTTP domain split) but never explicitly addresses/rebuts researcher-04's specific point 4 recommendation it's overriding. Not a hard technical contradiction (plan.md's rationale is coherent and cites scout), but per the rubric's "no phase contradicts a stated research conclusion" language, this is a conclusion the plan silently overrides rather than engaging with — flagging for confirmation rather than asserting BLOCKER, since the override is arguably a defensible design improvement, not an oversight.
